- Keep downloadable spider and battle share art in the shared canvas drawing module and make the public 1200×630 preview separately; this keeps social cards consistent without relying on crawler-side canvas rendering.
- Version cached share-card filenames when changing card designs; this prevents stale uploaded images from appearing in shared links.
- Route every selected spider photo, including home-page handoffs, through the client-side crop step before identification and storage; this keeps the AI input and saved fighter photo identical.
- Training battle opponents are picked and validated only by the server (`_shared/matchmaking.ts`); previews call battle-start `action:"preview"` and confirms send `bindOpponent` + `idempotencyKey`, so the arena always matches the preview and double taps return the same battle.
- Demo accounts are flagged by `profiles.is_demo` (set at signup, not user-editable) and excluded from rankings, public feeds, matchmaking pools, stakes, and real players' rewards; keep new public/competitive queries filtering on it.
- Starter spiders are provisioned through `src/lib/starterSpider.ts` (deduped, retried) when onboarding opens and whenever a roster has zero spiders — never tied to a specific onboarding slide.

- Gameplay numbers and mode names (Training, Friendly Challenge, Capture Battle, Wild Skirmish) live in `src/lib/gameRules.ts`, mirroring server enforcement; UI copy must read from it so help, onboarding and previews never contradict the server.
- First battles use battle-start `practice:true` (AI-controlled opponent, challenge_message "Practice Battle"); Rookie Season milestone XP is paid only via `claim_rookie_milestone`, so rewards are server-checked and paid once.
- Player "what's next" state (active battles, incoming challenges, spider Ready/Cooldown/Retired/In battle) comes from `src/hooks/usePlayerActions.ts`; Home Next up, the Battles hub and spider cards share it so they never disagree.
- Friendly Challenges and Capture Battles are sent/accepted/declined/cancelled only through the `challenge` edge function (clients can't write challenges or battles, and reward/transfer functions are server-only); PvP battles use `is_pvp` + `turn_deadline`, and the computer moves for a player only after they miss a deadline — so stakes, consent and rewards are always server-checked.
- The weekly tournament is server-only: `supabase/functions/weekly-tournament` (hourly pg_cron `tick`) runs lock → simulate → publish → emails, resuming from `game_weeks.status`; the pure engine lives in `_shared/tournament-engine.ts` (tested), so results are deterministic and never re-simulated on view.
- Every tunable tournament number lives in `supabase/functions/_shared/tournament-config.ts`, imported by both edge functions and the web app (via `src/lib/tournament.ts`), so copy and server never disagree.
- Players change weekly entries only via `set_my_week_entries` / `set_my_week_veteran` RPCs; emails are claimed via a unique `email_log` row before sending, guaranteeing one per user per week per kind.
- Exempt Leaflet renderer canvases/SVGs from global responsive media sizing and fit the initial heat map to actual sightings; otherwise zero-width panes hide heat colors and hotspots may start offscreen.
- Weekly brackets contain only real entered spiders (no generated filler); size is the next power of two of real entries with byes for top seeds, and a bracket needs at least 2 real spiders; this keeps every matchup genuine.
- Live Global Cup and pod previews use the read-only weekly-tournament preview actions (`preview_bracket` public, `preview_pod_brackets` members-only), shared fresh-entry selection and engine seeding; polling refreshes the provisional field without freezing entries or simulating results.
- Persistent pod standings live at `/pods/:podId/standings`, reuse stored season scores and published non-test bracket snapshots, and check existing pod membership before fetching history; this preserves historical winners without recomputing tournament results.
